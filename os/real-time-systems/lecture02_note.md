## 1. 複習：即時系統與嵌入式系統的組成

### 1.1 定義與安全氣囊例子

[00:00]–[01:32]

- 即時系統：描述它的行為時，要**定量**用到實體時鐘時間（wall clock time / physical time）。
- 行為怎麼描述：列出輸入、輸出、**時間限制**。
- 事件（event）由感測器產生 → 系統處理 → 回應送到致動器（actuator）。
- 例：車子偵測到碰撞，要在 **10 ms 內**打開安全氣囊。超時就算失敗，乘客會受傷。

### 1.2 三個組成：硬體、RTOS、應用程式

[02:03]–[03:00]

| 組成 | 內容 |
|---|---|
| 硬體 | CPU，接人機介面、感測器（類比 → 數位）、致動器（數位 → 類比） |
| 即時作業系統（RTOS） | 排程所有即時任務 |
| 應用程式 | 跑在 RTOS 上，算出理想的回應 |

回應改變外部環境，感測器再讀到新狀態，迴圈一直繞下去（第一講的控制迴圈）。

### 1.3 RTOS 和一般 OS 差在哪

[03:00]–[04:01]

- RTOS 讓程式在**有時間上限**的方式下執行（time-bounded）。
- 回應晚了，系統就算失敗。
- 一般 OS 追求**公平（fair）**，不保證時間。RTOS 的目標是**幫任務趕上 deadline**。

## 2. 嵌入式即時系統的特性

### 2.1 時間限制

[04:01]–[05:01]

- 不是所有任務都是即時的，但**一定有一些是**。
- 每個即時任務都有時間限制，輸出要在規定時間內產生。
- 一般程式沒有「幾毫秒內要給答案」這種要求，這是新的。

### 2.2 Fault、Error、Failure

[05:01]–[07:00]

三個詞意思不同：

| 詞 | 意思 | 冷氣例子【口頭】 |
|---|---|---|
| **Fault**（缺陷） | 系統裡某處和規格不符，偏設計面 | 冷氣的擺風功能壞了 |
| **Error**（錯誤） | 執行時出現的錯誤**內部狀態** | 按下擺風鍵，但沒擺風 |
| **Failure**（失效） | 錯誤影響到外部，系統沒做到該做的 | 我在意擺風，於是這台冷氣「失效」了 |

重點：

- Fault 可以一直藏著，不一定變成 error（從來不按擺風鍵就不會發生）。
- Error 不一定變成 failure（不擺風我也能接受）。
- [26:00]–[27:00] 老師後來補一句：**failure 也不一定造成 damage（損害）**。Word 當掉，但剛存過檔 → 沒損害；工作了 10 小時沒存 → 損害很大。
- 這些詞在不同應用裡意思會有點不同。

### 2.3 安全與任務關鍵性

[07:00]–[08:01]

- **Critical task**（關鍵任務）：它失效，整個系統就失效。例：飛機的高度感測器不工作 ⚠️（逐字稿為 "altitude sensor"）。
- **Safe system**：就算出錯，也不會造成損害。
- **Safety-critical system**（安全關鍵系統）：**任何一次**失效都可能造成嚴重損害。這門課主要關心這種。

【課本補充】課本 p.11 把 **task criticality** 定義成「任務失效的代價」。越關鍵越要可靠，失效時要立刻偵測、恢復。課本特別提醒：**關鍵性 ≠ 優先權**，關鍵性不決定執行順序（後面排程章節會講）。

### 2.4 並行、分散與回饋、客製硬體、反應式、穩定、例外處理

[08:01]–[11:01]

| 特性 | 說明 |
|---|---|
| **並行（concurrency）** | 要回應很多獨立事件，每種事件開一個任務。任務平行跑，同樣輸入可能得到不同結果（不確定性，non-determinism）。例：飛控的階層式系統 |
| **分散與回饋** | 車上 ECU 散在各處；感測器 → 計算 → 致動器 → 環境 → 感測器，形成回饋 |
| **客製硬體** | 常用專門為該用途設計的硬體 |
| **反應式（reactive）** | 和環境持續互動，不是「輸入一次、輸出一次、結束」 |
| **穩定（stability）** | 過載時（感測資料太多、任務太多），至少**最關鍵的任務**還要趕上 deadline |
| **例外處理** | 例外發生時要處理好 |

【課本補充】（p.11–12）

- **分散**：例如分布很廣的煉油廠，在資料源頭就地處理，再送到中央，避免網路過載。
- **客製硬體**：手機處理器只做手機需要的事，重點是省電；MPFI 引擎用 16 或 32 位元、約 40 MHz 的處理器就夠。
- **反應式**：一般系統是 `output = φ(input)`；反應式系統每一步的結果拿去改變環境，再取樣回來，計算可以看成**不會結束**。
- **穩定**：和一般系統要求的「公平」相反——過載時可以犧牲不重要任務的 deadline。
- **例外處理**：很多系統全天候無人值守（例：小型自動化化工廠）。失效要被偵測到，然後**優雅降級（gracefully degraded）**繼續跑，而不是突然停機。

## 3. 安全與可靠

### 3.1 一般系統：兩件獨立的事

[11:01]–[12:31]

- **安全（safe）**：失效時也不造成損害。
- **可靠（reliable）**：長時間運作不失效，失效機率低。
- 在一般系統裡，這是**兩個獨立的概念**。

【課本補充】（p.12）兩個反例：

| | 安全 | 可靠 |
|---|---|---|
| 文書處理軟體 | ✅ 當掉通常沒什麼損失 | ❌ 不太可靠 |
| 手槍 | ❌ 失效可能炸膛 | ✅ 很少失效 |

- 安全關鍵系統：任何失效都會造成嚴重損害，所以不想要任何失效。
- 系統**很少失效** → 損害也很少發生。安全和可靠就是這樣在這裡連在一起。

### 3.2 Fail-safe state

[13:00]–[15:00]

> **Fail-safe state（失效安全狀態）**：系統在這個狀態下失效，不會造成損害。（課本 p.13）

- 系統不可靠、常常失效 → 失效時把它帶到 fail-safe state。
- **紅綠燈**：控制器壞掉時，所有燈變成**黃燈閃爍**。駕駛看到就知道號誌壞了，會小心通過。
  - 【課本補充】全綠不行（會撞車）；全紅也不算——不會出事，但會讓交通全部卡住。
- **文書處理**：文件已存到磁碟、沒有未存的修改。這時當掉沒關係。
- 有 fail-safe state 時，可靠度再低都不影響安全。
- 好的設計可以**增加 fail-safe state 的數量**，但可能要很多額外硬體，很貴。

### 3.3 沒有 fail-safe state 的系統：只能靠可靠

[15:30]–[16:30]

- 有些系統**根本沒有** fail-safe state。
- 例：飛機的導航電腦。失效時「把引擎關掉」顯然不是安全狀態。
- 這種系統**唯一**提升安全的方法，就是**提升可靠**：不要失效，或失效得非常非常少。

【課本補充】（p.13）fly-by-wire 飛機的要求：每 **10⁹ 飛行小時最多 1 次失效**（約一百萬年連續飛行）。

## 4. 怎麼做出高可靠的系統

### 4.1 三招：避免、偵測移除、容錯

[16:30]–[17:30]

1. **錯誤避免（error avoidance）**：開發時就不讓錯誤發生。課本：好的軟體工程方法、設計方法、CASE 工具。
2. **錯誤偵測與移除（error detection and removal）**：課本：靠審查和測試找出來修掉。
3. **容錯（fault tolerance）**：系統內部有**冗餘（redundancy）**，出了錯也不變成錯誤的輸出。

課本強調：前兩招再怎麼做，實際系統也不可能完全沒錯，所以一定要容錯。

### 4.2 硬體容錯：BIST 與 TMR

[17:30]–[19:30]

**BIST（Built-In Self-Test，內建自我測試）**——老師以記憶體為例【口頭】：

```
寫入一個 pattern → 讀回來
  ├─ 讀回一樣 → 這一列（row）是好的
  └─ 讀回不一樣 → 這一列壞了
        → 把這個位址重新對應（remap）到備用列（spare row）
```

- 外面的人完全看不到這個 fault：位址還是同一個，只是背後換了一列。
- 課本 p.14：系統定期自我測試，偵測到失效就自動換掉壞元件、換上冗餘的好元件。

**TMR（Triple Modular Redundancy，三模冗餘）**——飛機常用：

```
          ┌─ 處理器 C1 ─┐
input ────┼─ 處理器 C2 ─┼─→ 投票電路 → 多數結果
          └─ 處理器 C3 ─┘
```

- 三個處理器拿同樣輸入，各自算，投票取多數。
- 一個壞了，另外兩個還對，投票電路把錯的「遮掉（mask）」。

【課本補充】（p.14）

- TMR 只能容忍**同時一個**元件出錯。兩個以上同時錯（修好之前），多數結果就是錯的。
- 要容忍同時 n 個元件失效，至少要 **2n + 1** 個冗餘元件。

### 4.3 軟體容錯：N-version programming 與 recovery block

[19:30]–[24:32]

**N-version programming**——TMR 的軟體版：

- 不同團隊各自寫同一個模組的 N 個版本，同樣輸入一起跑，結果投票。
- **為什麼效果不好** [22:30]–[23:30]：人其實很像。一群工程師覺得難的地方，另一群也覺得難，於是在**同樣的地方犯同樣的錯**。
  - 硬體故障通常是實體原因（例如某條線燒掉），各份獨立。軟體錯誤在邏輯層，會相關。
  - 課本稱為 **statistical correlation of failures**（失效的統計相關性）。

**Recovery block**——老師用 Java 的 try / catch / finally 來比喻：

```
try {
    一般的計算         // 任一行出錯 → 跳到 catch
} catch (...) {
    恢復：換一種方法算完、或交給別的函式，確保結果不是災難
}
```

課本的圖（p.15 Fig.12）：

```
input → TB1 → test ─成功→ result
             └失敗→ TB2 → test ─成功→ result
                         └失敗→ TB3 → … → 全失敗 → exception
```

- TB = try block。每個 try block 算同一件事，但**故意用不同演算法**。
- 每個結果過一個**接受測試（acceptance test）**。失敗就換下一個 try block。
- 老師提到 C++ 也有類似的機制 [24:01]。

| | N-version | Recovery block |
|---|---|---|
| 冗餘來自 | 不同**團隊** | 不同**演算法** |
| 執行方式 | **同時**跑，投票 | **一個接一個**，過接受測試就停 |

【課本補充】（p.15–16）recovery block 也有相關性問題。另外，try block 是一個接一個試的，所以只適合 **laxity 大**（deadline 遠大於執行時間）的任務。slack 很短的任務可能來不及；所以後面的 try block 常只放骨架程式碼，算個近似值，比較快。

### 4.4 【實測】TMR 投票：獨立故障 vs 相關故障

用 Python 模擬 100 萬次：每份拷貝出錯機率 p，投票取多數。另外加一個「共同模式」故障：機率 ρ 時**所有拷貝一起錯**（模擬 N-version 的相關錯誤）。

```python
def run(p, rho, n=3):
    bad = 0
    for _ in range(N):
        if random.random() < rho:          # 相關：每個版本都有同一個 bug
            outs = ['wrong'] * n
        else:
            outs = ['wrong' if random.random() < p else 'ok' for _ in range(n)]
        if vote(outs) != 'ok':
            bad += 1
    return bad / N
```

結果：

| 每份失效 p | 單份 | TMR 公式 3p²−2p³ | TMR 模擬（獨立） | TMR 模擬（ρ=0.005） |
|---|---|---|---|---|
| 0.01 | 0.0100 | 0.000298 | 0.000298 | **0.005228** |
| 0.1 | 0.1000 | 0.028000 | 0.028142 | 0.032793 |

另外：5 份冗餘（容忍 2 個，2n+1=5）、p=0.1、獨立 → 0.008698。

看到什麼：

- 故障獨立時，TMR 把 1% 降到 0.03%，和公式一致。
- 只要有 0.5% 的機會「大家一起錯」，TMR 的失效率就變成 0.52%，**幾乎全由相關故障決定**，冗餘的效果差不多沒了。這就是 N-version programming 效果不好的原因。

### 4.5 【課本補充】Checkpoint 與 rollback

（p.16，課堂沒講）

- 計算進行到一個有意義的段落，就檢查系統狀態。
- 檢查通過 → 把狀態存到穩定儲存（checkpoint）。
- 下一次檢查失敗 → 退回（rollback）上一個 checkpoint，從那裡重新算。
- 適合狀態可能被破壞的情況，例如資料損毀、處理器失效。

## 5. 嵌入式硬體

[24:32]–[26:00]

嵌入式系統裡通常有：

- **ASIC**（特定用途積體電路）、**FPGA**（可程式邏輯）
- 依用途而定的硬體：麥克風、喇叭、相機……
- **類比 I/O**：濾波、處理感測器輸入
- 記憶體
- 可程式處理器：**DSP**（數位訊號處理器，主要處理感測器輸入）、微控制器
- 感測器、致動器

它們用匯流排（bus）連起來，最常見的是 **ARM AMBA bus**（一個標準）。上面跑 RTOS，同時有即時與非即時的行程。

【口頭】[26:00] 這些元件內部，尤其記憶體和處理器，通常已經有相當程度的容錯。

## 6. 為什麼嵌入式裝置需要 OS

[27:00]–[29:00]

系統太複雜了。不一定要像伺服器 OS 那麼完整，但一定要有：

- **多工（multitasking）**：要有並行的行程
- **排程（scheduling）**
- **同步（synchronization）**

老師說這三項（投影片上的藍色部分）最重要，是讓即時系統成立的關鍵。另外還要：

- I/O 的排程與緩衝
- 安全性、電源管理

例：一支手機的 OS 約有 **500 萬行**程式碼。現代軟體一層疊一層的函式庫；稍微複雜一點的系統就需要很多層，所以需要一個接近筆電或伺服器 OS 功能的 OS。

## 7. 處理器、OS、程式語言的現況

### 7.1 處理器

[29:00]–[32:00]

老師說投影片的數據是 10–15 年前的，「但大致還成立」。

- 大多數嵌入式處理器**不是 64 位元**：用不到那麼大的記憶體。主流是 **16 和 32 位元**。
- 4 位元幾乎不存在了；8 位元是早期（登月之後 NASA 用的那一代）。
- 架構：
  - **ARM** 最普遍，銷售額上一直是嵌入式的老大。
  - **RISC-V** 正在快速興起。
  - PowerPC 以伺服器聞名，x86 以桌機聞名，但 Intel Atom 這類嵌入式產品也不錯。
  - **MIPS** 一直是嵌入式公司，但（到 2022 年）越來越被 ARM 擠下去。
- 幾乎所有嵌入式公司都得面對即時問題：只要把運算放進真實環境，就躲不掉。
- 現在很多嵌入式處理器是**多核心**，有完整的軟體支援（OS、編譯器、除錯工具）。

### 7.2 OS：RT Linux、商用 RTOS、開源的利弊

[32:00]–[34:32]

- 最有名的開源即時 OS：**Linux RT**（課程最後會講）。
- 很多商用系統還是用**商用 RTOS**。
- 嵌入式裝置**對成本非常敏感**：大量生產、要很便宜，所以開源越來越多。老師認為接下來 10 年，隨著 RISC-V 進來，這會是很有趣的領域。

開源 OS 的利弊：

| | 開源 | 商用 |
|---|---|---|
| 費用 | 免費 | 要錢 |
| 品質 | 不一定好：沒有全職開發和測試人員 | 有 |
| 裝置驅動支援 | 常常不夠 | 有 |
| 授權 | GNU GPL 等條款可能要求你**公開裝置的原始碼** | — |

商用 RTOS 例子：**Wind River**、**Microsoft 嵌入式**、**Symbian**、**QNX**。老師說現在選擇更多，後面再講。

### 7.3 【原始碼】Linux 的 PREEMPT_RT 選項

一般 Linux 和「即時 Linux」差在哪？v6.2.12 的 Kconfig 寫得很清楚：

`kernel/Kconfig.preempt:70`

```kconfig
config PREEMPT_RT
	bool "Fully Preemptible Kernel (Real-Time)"
	depends on EXPERT && ARCH_SUPPORTS_RT
	select PREEMPTION
	help
	  This option turns the kernel into a real-time kernel by replacing
	  various locking primitives (spinlocks, rwlocks, etc.) with
	  preemptible priority-inheritance aware variants, enforcing
	  interrupt threading and introducing mechanisms to break up long
	  non-preemptible sections. This makes the kernel, except for very
	  low level and critical code paths (entry code, scheduler, low
	  level interrupt handling) fully preemptible and brings most
	  execution contexts under scheduler control.

	  Select this if you are building a kernel for systems which
	  require real-time guarantees.
```

對照本講：

- RTOS 要「有時間上限」。一般 kernel 有很多**不能被搶占**的區段（例如拿著 spinlock 時），高優先權任務得等，等多久沒有上限。
- PREEMPT_RT 把 spinlock 換成可搶占、有**優先權繼承（priority inheritance）**的版本，中斷改成執行緒處理，讓幾乎所有執行情境都歸排程器管。優先權繼承在第 10–11 支（Priority Inversion、PIP and HLP）會講，第 23 支講 Linux-based RTOS。

⚠️ v6.2.12 裡只有 `arch/Kconfig:1166` **定義**了 `ARCH_SUPPORTS_RT`，沒有任何架構 `select` 它。所以光用這版主線原始碼**開不了** `PREEMPT_RT`，需要另外的 RT patch。

【實測】本機（Ubuntu 22.04 的 6.5.0-21-generic）：

```
CONFIG_PREEMPT_VOLUNTARY=y
# CONFIG_PREEMPT is not set
CONFIG_PREEMPT_DYNAMIC=y
```

`uname -v` 顯示 `PREEMPT_DYNAMIC`。也就是說，這是一般桌機核心：預設是 voluntary preemption（只在 kernel 主動檢查的點讓出），可以在開機參數換模式，但**不是** PREEMPT_RT。

### 7.4 程式語言

[34:32]–[35:31]

- 主流：**C、C++、組合語言**。
- 原因：控制力和可見度高；**沒有很重的背景工作**。
- Java 這類語言有垃圾回收（garbage collection）之類的背景工作，會搶 CPU 時間，即時需求就可能受影響。

⚠️ 逐字稿 [35:02] 把 Rust 和 Java 並列為「有昂貴背景工作」的語言。Rust 其實沒有垃圾回收，這裡可能是口誤或字幕錯誤；課本沒提，存疑。

### 7.5 未來

[35:31]–[36:16]

多核心、5G、IoT——這些新趨勢都需要即時系統。

## 8. 一頁速查表

### 8.1 嵌入式系統三組成

硬體（CPU、感測器、致動器）＋ RTOS（排程即時任務，**有時間上限**）＋ 應用程式。一般 OS 追求公平；RTOS 追求趕上 deadline。

### 8.2 名詞

| 名詞 | 一句話 |
|---|---|
| Fault | 和規格不符的地方（可能一直藏著） |
| Error | 執行時錯誤的內部狀態 |
| Failure | 外部看得到的失效 |
| Damage | 失效造成的損害（失效不一定有損害） |
| Critical task | 它失效 → 系統失效 |
| Safety-critical system | 任何失效都可能造成嚴重損害 |
| Fail-safe state | 在這裡失效不會有損害（黃燈閃、已存檔） |

### 8.3 安全 vs 可靠

- 一般系統：兩件獨立的事（文書軟體安全不可靠；手槍可靠不安全）。
- 有 fail-safe state：再不可靠也能安全。
- **沒有** fail-safe state（飛機導航）：安全只能靠可靠（10⁹ 小時 1 次失效）。

### 8.4 可靠的三招

避免 → 偵測與移除 → 容錯（冗餘）。

| 技術 | 層級 | 做法 | 弱點 |
|---|---|---|---|
| BIST | 硬體 | 自我測試，壞了換備用 | — |
| TMR | 硬體 | 3 份同時跑、投票 | 只容忍 1 個；n 個要 2n+1 份 |
| N-version | 軟體 | N 個團隊、投票 | 失效相關 |
| Recovery block | 軟體 | 不同演算法依序試、接受測試 | 失效相關；要 laxity 大 |
| Checkpoint/rollback | 軟體 | 存狀態，失敗退回 | — |

實測：0.5% 的相關故障就讓 TMR 從 0.03% 失效率變成 0.52%。

### 8.5 現況

16/32 位元為主；ARM 最大、RISC-V 興起。OS：Linux RT（開源）、Wind River / QNX 等（商用）。語言：C / C++ / 組合語言，避開 GC。Linux 的 `PREEMPT_RT`：可搶占鎖 ＋ 優先權繼承 ＋ 執行緒化中斷。

## 附：本講一句話總結

> **嵌入式即時系統 = 硬體 ＋ 有時間上限的 RTOS ＋ 應用程式；它有時間限制、並行、分散回饋、反應式、過載時要保住關鍵任務等特性。Fault（缺陷）不一定變成 error，error 不一定變成 failure，failure 也不一定造成損害。一般系統的安全和可靠是兩回事，有 fail-safe state（黃燈閃、已存檔）就能靠它換到安全；但飛機導航這類安全關鍵系統沒有 fail-safe state，安全只能靠極高的可靠度（10⁹ 小時 1 次失效）。做法是錯誤避免、偵測移除、加上冗餘容錯：硬體有 BIST 和 TMR（n 個同時壞要 2n+1 份），軟體有 N-version programming 和 recovery block，但軟體錯誤彼此相關，效果有限——實測只要 0.5% 的「大家一起錯」，TMR 的好處就幾乎沒了。現況是 16/32 位元的 ARM / RISC-V、C / C++，OS 有 Linux RT 和 Wind River、QNX 等商用 RTOS。**
