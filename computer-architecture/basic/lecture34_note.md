## 0. 本講地圖

本章（影片 Ch10）分四部分：記憶體系統概論 → cache → 記憶體系統的數學模型 → virtual memory。這講是第一部分。

```
之前的假設（不對）：
  ① 一個程式擁有整個記憶體      → 其實很多程式同時在跑（virtual memory 解決）
  ② 記憶體 = 一個大陣列，1 週期就能存取 → 其實又快又大做不到
技術的取捨：flip-flop（快、大、耗電）> SRAM > DRAM（慢、小、省）
人的習慣：時間局部性、空間局部性
  量時間局部性：stack distance     → 用 cache 階層（L1 → L2 → 主記憶體）
  量空間局部性：address distance   → 用 cache block（32/64/128 bytes 一起搬）
```

## 1. 我們之前做的兩個假設

[01:21]–[05:25]　課本 Ch11 開頭（p.505–506）

到目前為止，我們把記憶體看成：

- 一個**很大的 byte 陣列**，位址從 0 到 2³² − 1（32 位元系統），每個 byte 有自己的位址。
- **1 個週期**就能讀或寫。
- 寫組合語言時，**整個記憶體都屬於這一個程式**，想寫哪裡就寫哪裡。

這兩件事在真實世界都不成立：

| 假設 | 真實情況 |
|---|---|
| ① 一個程式擁有整個記憶體 | 很多程式**同時**在跑，要神奇地避免它們互相蓋掉 |
| ② 32 位元系統就有 4 GB 實體記憶體 | 實體記憶體可能只有 1 GB；64 位元系統的程式可能要 8 GB，卻只有 1 GB 實體記憶體 |

這些要到本章後半的 **virtual memory**（虛擬記憶體）才解決（第 37 支）。

## 2. 同時有很多程式在跑

[05:25]–[08:22]　課本 p.505

【口頭】[05:40] 老師給大家看他 Windows 工作管理員的截圖：Skype 用 89 MB、PowerPoint 用 79.8 MB……一共 **74 個 process**。

- **Process**（行程）：一個正在執行的程式。
- 一顆處理器**一次只跑一個**程式，但會**定期切換**：跑程式 1、切到程式 2、切到程式 3、再切回來。
- 每個程式都以為整個記憶體是它的 → 可能**重疊**：一個程式寫的位址，另一個程式不小心也寫同一個位址。一定要避免。

【課本補充】p.505：
- 桌機、筆電通常跑 A 幾毫秒、跑 B 幾毫秒，來回切換。使用者感覺不到，因為切換的時間尺度比人腦能察覺的還小：影片每秒 30 張畫面，也就是每 33 毫秒一張；處理器在 33 毫秒內處理完下一張畫面，剩下的時間就能跑別的程式。
- **作業系統**是一個特別的程式，幫處理器管理自己和其他程式，例如 Windows、Linux。

## 3. 記憶體不可能又快又大

[08:22]–[15:05]　課本 §11.1.1（p.506–507，Table 11.1）

可以用來做記憶體的技術（[第 20 支](lecture20_note.md)）：

| 單元 | 面積 | 一個陣列的典型延遲 |
|---|---|---|
| Master-slave D flip-flop | 0.8 µm² | 不到一個週期 |
| SRAM cell | 0.08 µm² | 1–5 週期 |
| DRAM cell | 0.005 µm² | 50–200 週期 |

⚠️ 自動字幕把數字的「0.」吃掉了，聽起來像「8 micron square」「05 micron square」；上表用課本 Table 11.1 的數字。【口頭】[10:07]「這些數字有點舊（課本寫 2012 年），但**比例**現在還是一樣」。

- flip-flop 是 SRAM 的 **10 倍**大，SRAM 是 DRAM 的 **16 倍**大 → 同樣的面積，DRAM 可以放 **160 倍**的資料。
- 但 DRAM 也慢了大約 200 倍。
- 結構複習：DRAM = 1 個電容（加 1 個電晶體）；SRAM = 交叉耦合的反相器；D flip-flop = 兩組交叉耦合的 NAND 閘再加一些電路。

**三角取捨**（【口頭】[13:31]）：

```
面積 ↑ → 延遲 ↓，但功耗 ↑
要更快 → 面積 ↑、功耗 ↑
要省電 → 更小、更慢
```

「不可能什麼好處都有，這幾乎是哲學。」

- 全部用 flip-flop：同樣的晶片面積只放得下很少的 bit，又很耗電。
- 全部用 DRAM：放得很多，但每次存取都很慢。

【課本補充】p.507：
- 2012 年的技術做不出超過 400–500 mm² 的晶片，所以晶片上的記憶體有限；晶片外的記憶體要幾十個週期才能存取。
- DRAM 很難和處理器做在同一顆晶片上，所以晶片上的記憶體只能用 SRAM。
- 假設全部用 DRAM、延遲 100 週期、1/3 的指令是記憶體指令：完美 5 級 pipeline 的 CPI = 1 + 1/3 × (100 − 1) = **34**，「完全不能接受」。
- 如果存取完全隨機，就沒救了；如果存取**有某種規律**，就有機會兩全其美。

## 4. 記憶體延遲取決於什麼

[15:05]–[17:21]

【口頭】記憶體延遲取決於三件事，都是我們能控制的：

| 因素 | 說明 |
|---|---|
| **大小** | 4 KB 的記憶體很快，4 MB 的就相當慢 |
| **埠的數量** | 暫存器檔：一條指令同一週期讀 2 個、寫 1 個 → 2 讀埠 1 寫埠。一週期發 2 條指令的處理器要 4 讀埠 2 寫埠 = 6 個埠。埠越多（同時存取越多），越慢、越耗電 |
| **技術** | SRAM、DRAM 還是 flip-flop |

## 5. Sophia 的書桌、書架和櫃子

[17:21]–[24:21]　課本 §11.1.2（p.507–508）

【口頭】[17:35] 學生 Sophia 的工作環境：

| | 大小 | 拿一本書要多久 | 放什麼 |
|---|---|---|---|
| 書桌 | 最小 | 最快（伸手就到） | **最常用**的書（例如考試要用的） |
| 書架 | 中 | 中（走 10 步） | 比較少用的參考書 |
| 櫃子（房間另一頭） | 最大 | 最慢 | 很少讀的書，數量很多 |

```
大小：書桌 < 書架 < 櫃子
速度：書桌 > 書架 > 櫃子
```

考前幾天，她會**一直重複讀同一批書**。所以大概 90% 的時候從書桌拿到；剩下 10% 裡的 9% 從書架拿到；只有 1% 要走去櫃子。

【口頭】[23:13] 廚房也是這樣：流理台上放鹽和糖；冰箱放蔬菜和肉；很少用的材料（例如番紅花）乾脆不放家裡，要用再去市場買。

【課本補充】p.507–508：課本是作者自己的例子：他桌上堆滿書；上學期教計算機架構，所以架構的書放桌上，分散式系統的書放旁邊的小書架，從來不讀的哲學書放到角落的大櫃子。這學期改教分散式系統，就把那批書一次拿到桌上，架構的書移回書架。超市把香料放在蔬菜旁邊，浴室用品和電器放很遠，也是同樣的道理。

## 6. 時間局部性與空間局部性

[24:21]–[28:24]　課本 Definition 97（p.508）

【口頭】[24:41] 計算機架構課結束後，架構的書回到書架；考完試要去度假，**度假規劃的書**被拿到桌上。她不會為了每一本旅遊書各跑一趟（本來想去歐洲，後來改去新加坡），而是**一次把全部旅遊書抱過來**。用了一本，很可能馬上要用類似的另一本。

【口頭】[26:15] 做咖哩：拿了薑，半分鐘後大概就要蒜和辣椒粉，所以一次把香料全拿過來。

| | 定義 |
|---|---|
| **時間局部性**（temporal locality） | 一個資源在某個時間被存取，**很可能在短時間內再被存取** |
| **空間局部性**（spatial locality） | 一個資源在某個時間被存取，**很可能不久後會存取類似的資源** |

「temporal」是「time」的形容詞。

【課本補充】p.508–509：
- 課本問的關鍵問題：「記憶體存取有沒有時間和空間局部性？」有的話就能做關鍵的最佳化。
- **指令**的局部性很好分析：
  - 經驗法則：**90% 的程式碼只跑 10% 的時間，10% 的程式碼跑 90% 的時間**（例如文書處理器處理輸入、顯示的程式碼，比顯示說明畫面的程式碼常跑得多）→ 時間局部性。
  - 沒有分支時下一條是 PC + 4；分支的目標通常也不遠（迴圈或 if 的長度，大多 10–100 條指令）→ 空間局部性。

## 7. 量時間局部性：stack distance

[28:24]–[33:20]　課本 §11.1.4（p.509–511，Fig 11.1）

**Stack distance**（堆疊距離）的算法：
1. 維護一個存放記憶體位址的 stack（後進先出）。
2. 每次存取一個位址，就在 stack 裡找它。
3. 找到了：**距離 = 它離 stack 頂端幾格**。把它拿出來，放回頂端。
4. 沒找到：距離 = ∞（影片）。

距離小 → 一樣的位址一直被重複用 → **時間局部性高**。距離大 → 位址用得很隨機。

【口頭】[31:04] 影片的圖（一組 Perl 程式）：機率最高的兩格都在 20 以下。「如果我存取了一個位址，很可能在接下來 20 次存取內再存取它。」加起來大約 60% 的位址在 50 次存取內會再被用到。

**為什麼會這樣**（【口頭】[32:14]）：來自我們**寫程式的方式**。函式裡有 for 迴圈一直跑，同一組位址被一再存取；接著另一個迴圈又一再存取另一組。

【課本補充】p.509–510：
- 頂端的距離是 0，第 100 個是 99。
- 實際上 stack 有**深度上限 L**；新位址進來時若超過 L，就把最底下的丟掉。沒找到時距離記成 **L**（因為分不出是新位址還是被擠掉的舊位址）。
- 課本的實驗：SPEC2006 的 **Perlbench**（ref 資料集、split-mail 輸入）。前 100 萬次存取暖身（只維護 stack 不計數），接下來 100 萬次才計數；L = 1000。
- 結果：0–9 最常見，約 **27%**；超過**三分之二**小於 100。之後慢慢變少但不會變 0：**heavy-tailed distribution**（重尾分佈）。
- Trivia 3：研究者試過用 **log-normal 分佈**來近似 stack distance。

⚠️ 影片口頭說「約 60% 在 50 以內」；課本寫「27% 在 0–9、超過三分之二在 100 以內」。兩者描述的是同一張圖的不同切法，不衝突。

## 8. 量空間局部性：address distance

[33:20]–[42:31]　課本 §11.1.5（p.511–512，Fig 11.2）

**Address distance**（位址距離）：維護**最近 K 次**存取的滑動視窗。第 i 次存取的 address distance = 它的位址 − 視窗裡**最接近**它的那個位址。

例子（K = 10）：存取 104，最近 10 次裡沒有 104，但有 100 → 距離 = **4**。

**為什麼要用視窗，不直接和上一次比？**（【口頭】[35:28]–[39:44]）

```c
for (i = ...) {
    x = vals[i] + 常數 + 別的東西 + ...;   // 中間還會存取其他變數
    ...
}
```

- 下一圈存取 `vals[i+1]` 時，**上一次**存取的可能是別的變數，不是 `vals[i]`。
- 但在最近 K 次裡一定找得到 `vals[i]`，它和 `vals[i+1]` 差一個 int = **4 bytes**。
- 所以看視窗裡最近的那個，才量得到「我剛剛在附近」。

**空間局部性從哪來**（【口頭】[40:52]）：
- 陣列、字串：for 迴圈依序掃過。
- 區域變數：`int i, j, k;` 編譯器通常給它們**連續的位址**（同一個 activation block），i 之後 4 bytes 是 j、再 4 bytes 是 k。
- linked list 的節點如果配置在一起也是。

【口頭】[40:15] 影片的圖：機率最高的在 0 附近，**超過 50%** 的存取在 ±25 bytes 以內。「如果我存取位址 X，不久後很可能存取 X ± Δ，Δ 很小。」

【課本補充】p.511：
- K 要選得好，不能太小也不能太大；經驗上 **K = 10** 對很多程式都適合。
- Perlbench 前 100 萬次：超過**四分之一**在 ±5，超過**三分之二**在 ±25；超過 ±50 之後慢慢變少，也是重尾分佈。
- p.512：幾千個程式（遊戲、文書處理、資料庫、試算表、天氣模擬、金融、手機應用）都有很高的時間與空間局部性：「這是人的基本特質」。當然可以故意寫出沒有局部性的程式，但那是例外；**要為常態設計，不是為例外設計**。

## 9. 利用時間局部性：cache 階層

[42:31]–[47:00]　課本 §11.1.7（p.512–514，Fig 11.3，Definition 98–99）

```
處理器 → L1 cache（書桌）→ L2 cache（書架）→ 主記憶體（櫃子）
```

| 層 | 對應 | 做法 | 影片的數字 | 課本的數字 |
|---|---|---|---|---|
| L1 | 書桌 | 小、SRAM | 1–2 週期；16 KB（16–32 KB） | 8–64 KB；1–2 週期 |
| L2 | 書架 | 較大、SRAM | 256 KB–4 MB；10 週期（例題） | 128 KB–4 MB；5–15 週期 |
| 主記憶體 | 櫃子 | 很大、**DRAM** | 4–32 GB | 100–300 週期 |

- **Cache**（快取）：整個記憶體的一個**小子集**。
- **主記憶體**（main memory，也叫 physical memory 實體記憶體）：包含**所有**記憶體位置的值。【口頭】[46:28]「之後可能會放寬，但現在先當成金科玉律。」例如系統有 20 億個記憶體位置，主記憶體全部都有；L1 可能只有幾千個，L2 幾百萬個。
- L1 為什麼快：做得**小**（小 = 快），用 SRAM（flip-flop 太貴）。

【口頭】[50:13] 很多大處理器還有 **L3**；有些有 **L4**，但很少見。

【課本補充】p.513：Intel Sandybridge 有 L3（4 MB 以上）。現在也有用 **non-volatile**（非揮發性）記憶體做主記憶體的。

## 10. Inclusive cache 與存取流程

[47:00]–[50:47]　課本 Definition 100–101（p.513–514）

**Inclusive cache hierarchy**（包含式 cache 階層）：

```
L1 的位址 ⊂ L2 的位址 ⊂ 主記憶體的位址（全部）
S1 ⊂ S2 ⊂ S
```

不會有一個位址在 L1 卻不在 L2，也不會在 L2 卻不在主記憶體。

**存取流程**：
1. 先找 L1。有 → **cache hit**（快取命中），直接讀或寫。
2. 沒有 → **cache miss**（快取未命中），送請求給 L2。
3. L2 有就拿給 L1；L2 也沒有就送給主記憶體。
4. 主記憶體一定有。拿回來後**填進上面各層**。可以遞迴下去（L1 → L2 → L3 → 主記憶體）。

L1、L2 通常在**處理器晶片裡面**；主記憶體是晶片外另一個模組。

⚠️ 包含式和非包含式，兩邊說法不太一樣：
- 影片 [48:05]：「一般來說 inclusive 比較好；non-inclusive 會造成很多問題，比較是研究題目，不是教科書題目。」
- 課本 v3.09 p.513：inclusive「幾乎普遍使用」，因為好設計、簡單，還有一些第 12 章（課本）才講的正確性問題；但也說「有些進階處理器（截至 2025 年）用 **exclusive** cache，特別是能從彈性的資料擺放得到好處時」。課本把不遵守嚴格包含的都叫 exclusive。
- 本機：`lscpu`／`getconf` 只看得到大小（L1d 48 KB、L2 1.25 MB、L3 24 MB），看不出是不是 inclusive，這裡「待補」。

【課本補充】p.514：寫入時可以只寫 cache 然後繼續，或把修改傳到下層；寫入策略在 §11.2.3（第 35 支）。即使最後 miss，L1 的那 1 個週期也已經花掉了，因為事先不知道會不會 hit。

## 11. 階層的好處：算平均延遲

[50:47]–[52:41]　課本 Example 147（p.515）

**影片的例子**：

| 層 | hit rate | 延遲 |
|---|---|---|
| L1 | 95% | 1 週期 |
| L2 | 60% | 10 週期 |
| 主記憶體 | 100% | 300 週期 |

【口頭】95% 的存取只花 1 週期；3% 多花 10 週期；2% 再多花 300 週期。「這些數字很粗略」，之後會仔細算。

影片沒算出平均值，這裡我照課本 Example 147 的方法自己算：

```
T = 1 + 0.05 × (10 + 0.4 × 300) = 1 + 0.05 × 130 = 7.5 週期
全部去主記憶體：300 週期 → 快 40 倍
```

**課本 Example 147**：L1 miss rate 10%、1 週期；L2 miss rate 10%、10 週期；主記憶體 100 週期。

```
T = 1 + 0.1 × (10 + 0.1 × 100) = 1 + 1 + 1 = 3 週期
平的（只有主記憶體）= 100 週期 → 快 33.3 倍
```

重點：**大部分存取在最上層（最快）就命中**，越往下越少。設計目標是讓**越少的存取**掉到最下層。

【課本補充】p.515：效能提升取決於各層的 hit rate 和延遲；hit rate 取決於程式的 stack distance 分佈和 cache 管理策略；延遲取決於製造技術、cache 設計和管理策略。過去二十年這方面的論文有好幾千篇。

## 12. 利用空間局部性：cache block

[52:41]–[57:10]　課本 §11.1.8（p.515–516，Definition 102，Way Point 9）

既然大部分存取都在 ±20–25 bytes 內，就把記憶體切成**每 n bytes 一組**：

- 每組叫 **cache block** 或 **cache line**（快取區塊／快取行）。
- 是**不可分割**的單位（atomic unit）：整個 block 一起從下層搬上來，也整個一起被趕出去。
- 大小通常是 **32、64、128 bytes**，一定是 **2 的次方**（定址方便）。

【口頭】[54:27] 例子：切成 64 bytes 一塊：0–63、64–127……。程式先存取位址 100，依照 address distance 的圖，不久後很可能存取 75–125 附近。把整個 64-byte block 一次搬到 L1，後面的存取就都 hit，不用離開 L1。「就像 Sophia 一次拿全部旅遊書。」如果 block 裡是陣列，從一個位址開始很可能會掃過整個陣列。

【課本補充】p.516：
- 所以 cache 的一個 entry 不是一個位址，而是**一個 cache line**。
- L1 和 L2 的 line 大小可以不同；為了保持 inclusive、減少額外存取，L2 的 line 通常**等於或大於** L1 的。

**Way Point 9**（p.516）的五點，就是這講的總結：
1. 時間和空間局部性是大部分人類行為的特質，讀書和寫程式都一樣。
2. 時間局部性用 stack distance 量，空間局部性用 address distance 量。
3. 記憶體系統要設計成能利用這兩種局部性。
4. 時間局部性 → cache 階層：L1 小而快，滿足大部分存取；下層存更多、較少被用到、較慢。
5. 空間局部性 → 把連續的位置分成 block（line），block 是 cache 裡不可分割的單位。

## 13. 【原始碼】Linux 的 cache line 大小

Linux 核心在編譯時就要知道 cache line 多大，用來對齊常用的資料結構，避免一個結構橫跨兩個 line。`linux-src/arch/x86/include/asm/cache.h:7-9`：

```c
/* L1 cache line size */
#define L1_CACHE_SHIFT	(CONFIG_X86_L1_CACHE_SHIFT)
#define L1_CACHE_BYTES	(1 << L1_CACHE_SHIFT)
```

`linux-src/arch/x86/Kconfig.cpu:318-322`：

```
config X86_L1_CACHE_SHIFT
	int
	default "7" if MPENTIUM4 || MPSC
	default "6" if MK7 || MK8 || MPENTIUMM || MCORE2 || MATOM || MVIAC7 || X86_GENERIC || GENERIC_CPU
	default "4" if MELAN || M486SX || M486 || MGEODEGX1
```

- 一般 x86-64（GENERIC_CPU）：2⁶ = **64 bytes**。
- Pentium 4：2⁷ = 128 bytes；很老的 486：2⁴ = 16 bytes。剛好落在影片說的 32–128 範圍兩端附近。
- `linux-src/include/linux/cache.h:41` 再用它定義 `____cacheline_aligned`，讓變數對齊到一個 line 的開頭：

```c
#define ____cacheline_aligned __attribute__((__aligned__(SMP_CACHE_BYTES)))
```

## 14. 【實測】

程式在 `experiments/lecture34/`。

### 14.1 本機的 cache 階層

```
$ getconf -a | grep CACHE
LEVEL1_ICACHE_SIZE                 32768
LEVEL1_DCACHE_SIZE                 49152
LEVEL1_DCACHE_LINESIZE             64
LEVEL2_CACHE_SIZE                  1310720
LEVEL3_CACHE_SIZE                  25165824
LEVEL4_CACHE_SIZE                  0
```

| 層 | 本機 | 影片 | 課本 |
|---|---|---|---|
| L1d | 48 KB（另有 32 KB 指令 cache） | 16–32 KB | 8–64 KB |
| L2 | 1.25 MB | 256 KB–4 MB | 128 KB–4 MB |
| L3 | 24 MB | 「很多大處理器有」 | 4 MB+ |
| L4 | 沒有 | 「很少見」 | — |
| line | 64 bytes（每一層都是） | 32/64/128 | 32–128 |

各層的延遲在[第 20 支](lecture20_note.md#13-實測)用 pointer chasing 量過：L1 約 1 ns、L2 約 3–4 ns、L3 約 8–23 ns、DRAM 約 80–95 ns。

### 14.2 真實程式的 stack distance 與 address distance

用 valgrind 的 lackey 工具，記錄 `gzip` 和 `sort` 處理一個 166 KB 文字檔（課本 Ch11 的文字）時的每一次 load／store 位址；`locality.py` 照課本的方法算（暖身 100 萬次、計數 100 萬次、L = 1000、K = 10）：

```
$ valgrind --tool=lackey --trace-mem=yes sort in.txt 2>&1 >/dev/null | grep -E '^ [LSM] ' | head -2500000 > sort.trace
$ python3 -I locality.py sort.trace
```

| | sort | gzip | 課本 Perlbench |
|---|---|---|---|
| stack distance 0–9 | 37.5% | 11.2% | 約 27% |
| stack distance < 100 | **91.6%** | 33.8% | 超過 2/3 |
| 1000 格內找不到 | 1.5% | **54.3%** | — |
| address distance ±5 | 42.7% | 34.2% | 超過 1/4 |
| address distance ±25 | **76.2%** | 45.0% | 超過 2/3 |

- **sort** 的兩個分佈和課本很像，甚至更集中：時間和空間局部性都很高。
- **gzip** 的時間局部性看起來很差：一半以上的位址在最近 1000 個不同位址裡都找不到。原因：gzip 從頭到尾**掃過**輸入，每個 byte 大多只讀一次。
- 但 gzip 的空間局部性還不錯：最常見的 address distance 是 **0**（10.9%）和 **+1**（10.5%），就是一個 byte 一個 byte 往後讀。

**換成以 64-byte block 為單位**再算一次 stack distance（`locality.py x.trace line`）：

| | 以位址計 0–9 | 以 block 計 0–9 | 以位址計找不到 | 以 block 計找不到 |
|---|---|---|---|---|
| gzip | 11.2% | **50.8%** | 54.3% | **9.4%** |
| sort | 37.5% | **95.0%** | 1.5% | 0.0% |

gzip 換成 block 之後，「找不到」從 54% 掉到 9%。這就是 §12 的道理：**把相鄰位址綁成 block，空間局部性就變成 block 層級的時間局部性**，cache 就能命中。

⚠️ 這兩個程式和課本的 Perlbench 不同，數字只是示意；而且 lackey 的 trace 包含程式啟動時動態連結器的存取（前 100 萬次暖身大致蓋過這段）。

### 14.3 看見 64-byte 的 cache block

`stride.c`：在 512 MB 的陣列上（遠大於 24 MB 的 L3），每隔 stride bytes 讀 1 個 byte，讀 2²⁴ 次。綁在 CPU 2 上：

```
$ gcc -O2 -o stride stride.c && taskset -c 2 ./stride
stride    1 B :   0.48 ns per read   (64 reads per 64-B block)
stride    2 B :   0.49 ns per read   (32 reads per 64-B block)
stride    4 B :   0.51 ns per read   (16 reads per 64-B block)
stride    8 B :   0.62 ns per read   (8 reads per 64-B block)
stride   16 B :   0.94 ns per read   (4 reads per 64-B block)
stride   32 B :   1.44 ns per read   (2 reads per 64-B block)
stride   64 B :   2.60 ns per read   (1 reads per 64-B block)
stride  128 B :   4.37 ns per read   (1 reads per 64-B block)
stride  256 B :   5.26 ns per read   (1 reads per 64-B block)
stride  512 B :   5.57 ns per read   (1 reads per 64-B block)
```

- stride 小於 64 時，好幾次讀取落在同一個 block：只有第一次要從下層搬，其他都 hit → 很快。
- stride 1 到 64，每次讀取的時間大約隨「每個 block 被讀幾次」變少而變長（0.48 → 2.60 ns）。
- 都比 pointer chasing 量到的 DRAM 延遲（約 90 ns）快很多：依序往前讀時，硬體 **prefetcher**（預取器，猜你接下來要哪些 block，先搬上來）會提早把 block 搬好。
- ⚠️ 64 → 128 還在變慢，不是在 64 就停住。我的推測：Intel 的 prefetcher 有一種會連「相鄰的那一個 block」一起抓（等於 128 bytes 一組），stride 128 以上就沒得沾光。這裡沒有直接證據，「待補」。

| 空間局部性 | 用了一個，很快會用附近的 |

| Address distance | 和最近 K 次存取中最接近位址的差；小 → 空間局部性高；K = 10 |

## 附：本講一句話總結

> **我們之前假設一個程式擁有全部記憶體、而且記憶體又大又只要 1 週期，兩個都不對：真實系統同時跑幾十個 process（之後用 virtual memory 解決），而 flip-flop、SRAM、DRAM 的面積差 10 倍、16 倍，延遲從不到 1 週期到 50–200 週期，大小、延遲、功耗不能兼得。幸好人寫的程式和 Sophia 擺書一樣有規律：時間局部性（剛用過的很快會再用，用 stack distance 量）和空間局部性（用了一個很快會用附近的，用 K = 10 的 address distance 量），課本 Perlbench 有 27% 的 stack distance 在 0–9、超過三分之二的 address distance 在 ±25 bytes 內。所以用 cache 階層利用時間局部性（L1 小而快像書桌、L2 像書架、DRAM 主記憶體像櫃子，L1 ⊂ L2 ⊂ 主記憶體，miss 就往下一層找），用 32–128 bytes 的 cache block 一次搬一整塊來利用空間局部性。實測 sort 的局部性和課本很像，gzip 以位址看時間局部性很差，但換成 64-byte block 後 50.8% 的 stack distance 落在 0–9；本機 L1d 48 KB、L2 1.25 MB、L3 24 MB、line 64 bytes，Linux 也用 `L1_CACHE_SHIFT = 6` 對齊資料。**
