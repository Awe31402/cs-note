> 李允中《軟體工程》第 5 章（僅作目錄）。主要依據：Sommerville 9e Ch.22–23、Pressman 9e Ch.24–26。

## ① 核心原則

| 原則 | 說明 | 出處 |
|---|---|---|
| 風險管理 | 識別、分析、規劃、監控風險 | Sommerville Ch.22 §22.1；Pressman Ch.26 |
| 主動式風險策略優於被動 | 事先規劃，而不是出事才處理 | Pressman Ch.26 §26.1 |
| 專案排程 | 把工作拆成任務，估計時間與依賴關係 | Sommerville Ch.23 §23.3 |
| 敏捷規劃 | 以短迭代與可交付成果為單位規劃 | Sommerville Ch.23 §23.4 |
| 估算技術 | 依經驗或演算法模型估算；估算本身有不確定性，要隨專案進行修正 | Sommerville Ch.23 §23.5；Pressman Ch.25 |

## ② AI 開發中如何落地

**單人加 AI 版本**：沒有團隊管理問題（Sommerville Ch.22 §22.2–22.3 大多不適用），重點變成：

### 1. 任務大小要配合 AI 的能力
- 一個任務應該是 **AI 一次能完成、並能自動驗證**的大小。
- 太大：AI 的 context 塞不下所有相關程式碼，開始猜測。
- 太小：我花在下指令與審查的時間比 AI 寫程式還多。
- 經驗法則（待實際校準）：一個任務只動一個模組，並對應一到兩條驗收條件。

### 2. Context 預算
- AI 每次能看到的內容有限。規劃時要考慮：完成這個任務需要讀哪些檔案？
- 模組化設計（[04](./04-design.md)）直接降低每個任務的 context 需求。

### 3. 時間碎片化
- 每週 8 小時，切成 2 小時時段。每個時段結束前留下交接紀錄，讓下次（以及 AI）能快速接手。

### 4. 估算與校準
- 目前沒有 AI 輔助開發速度的可靠數據，所以**不從行數推算時間**。
- 每階段記錄實際小時數與行數，用來校準之後的估算（[`roadmap.md#時程估算`](../project/roadmap.md#時程估算)）。

## ③ 對應的自動化檢查

| 檢查 | 做法 |
|---|---|
| **Definition of Done 清單** | PR 範本列出完成條件（測試、lint、需求 ID、文件），CI 檢查可自動化的部分 |
| issue 範本 | 每個任務必須填寫驗收條件與預期修改的模組 |
| 時間與產出紀錄 | 每個時段的交接紀錄；階段回顧時統計（可用腳本從 git log 計算行數） |
