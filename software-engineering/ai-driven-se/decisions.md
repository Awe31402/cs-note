# 決策紀錄（Decision Log）

> 類 ADR（Architecture Decision Record）格式。每條決策固定包含：**背景 → 選項 → 決定 → 理由 → 代價**。
>
> 已定案的決策不輕易重新討論。如果執行中發現重大問題，新增一條決策取代舊的，並在舊決策標註「已被 D-xxx 取代」，不直接改寫舊內容。這是 [08 建構管理](./notes/08-configuration-management.md) 的變更追溯原則。

## D-001 專案類型：選擇產品型應用（E 類）

- **日期**：2026-11-19
- **狀態**：✅ 已定案

**背景**
需要一個約十萬行的實戰專案。規模要大到 AI 無法一次掌握，才能驗證軟體工程原則的作用。選題標準有三個：能自然拆成多個子系統、行為能客觀驗證、需求會逐步演進。

**選項**
| 選項 | 優點 | 缺點 |
|---|---|---|
| A. 關聯式資料庫引擎 | 可驗證性最高（sqllogictest、可與 SQLite 對照） | 需求演進來自技術而非使用者 |
| B. 程式語言與編譯器 | golden test 容易寫 | 語言設計容易無限發散 |
| C. 教學用作業系統 | 貼近既有筆記（OS、RISC-V） | AI 低階除錯能力弱，並行 bug 難重現 |
| D. 分散式 KV（Raft） | 練並行與共識 | 核心只有兩到三萬行，難撐到十萬行 |
| **E. 產品型應用** | 最接近業界，需求自然演進 | UI 與使用體驗不易客觀驗證 |

**決定**：選 E。

**理由**
- E 的主要疑慮是「驗證」，而 Lauren Tan 的倒金字塔方法正是在產品型應用（Electron + React 桌面 app）上實戰過的驗證策略（見 [D-006](#d-006-品質策略倒金字塔單人縮小版)）。
- 把模糊需求寫成可驗證的驗收條件，本身就是第 2 章需求工程的核心練習。
- 能練到最完整的軟體工程範圍。

**代價**
- 前期要花大量時間建立驗證環境，而不是直接開發功能。
- UI 與使用體驗仍需要人看驗證產物（錄影、截圖）來把關，無法完全自動化。

## D-002 題目：英文數位單字卡

- **日期**：2026-11-19
- **狀態**：✅ 已定案

**背景**
E 類專案需要具體題目。我自己正在學英文。

**決定**：英文數位單字卡平台，並追蹤學習進度。

**理由**
- **我自己就是真實使用者**，需求會從實際使用中自然長出來，能練到真實的需求演進。
- 領域內有真正複雜的子系統（排程演算法、離線同步、語音），不必為了湊行數硬塞功能。
- 選英文而不是日文等語言：不需要處理假名與漢字讀音，發音與字典資源也最豐富，可以把複雜度留給軟體工程本身。

**代價**
- 市面上已有成熟產品（例如 Anki），容易不自覺模仿它們的設計，要注意授權問題（見 [D-007](#d-007-不複製-anki-原始碼)）。

## D-003 九個子系統全部保留，分階段開發

- **日期**：2026-11-19
- **狀態**：✅ 已定案

**背景**
單純的單字卡 app 大約只有一到兩萬行。要達到十萬行，必須納入這個領域真正複雜的部分。

**選項**
- 只做核心功能（約兩萬行）：達不到「AI 無法一次掌握」的規模。
- 九個子系統一次規劃、一次開發：風險太高，而且每週只有 8 小時，很久都不會有可用的成品。
- **九個子系統全部保留，分階段開發**。

**決定**：九個子系統全部保留，分 P0 到 P6 共七個階段開發，詳見 [`project/roadmap.md`](./project/roadmap.md)。

**理由**
- 第一階段（MVP）就能每天使用，回饋迴路短。
- 後續階段依照實際使用時的痛點調整優先順序，能練到需求演進與第 5 章專案計畫。
- 每個階段都會累積 lint 規則，品質護欄跟著程式碼一起長大。

**代價**
- 早期的架構決策（例如資料模型）必須預留同步、多平台的擴充空間，否則後期重構成本高。

## D-004 技術棧：方案 B+（C++ 核心 + TypeScript UI）

- **日期**：2026-11-19
- **狀態**：✅ 已定案

**背景**
主要學習目標之一是**把 C++ 練好**。但 E 類專案的 UI 若要在瀏覽器執行，主流做法只有 TypeScript / JavaScript。

**選項**
| 選項 | C++ 佔比 | 優點 | 缺點 |
|---|---|---|---|
| A. 全 C++（Qt / QML） | ~90% | C++ 練得最多 | Qt 的 UI 測試與「AI 操作 app 驗證」工具較不成熟 |
| B. C++ 核心 + TS 介面與後端 | ~40–50% | 平衡 | C++ 練習量不夠 |
| **B+. 除 UI 外全部 C++** | **~70–80%** | C++ 練習量大，UI 仍能快速迭代 | 兩套工具鏈 |
| C. 全 TypeScript | 0% | 最貼近 Lauren Tan 的做法，AI 最熟悉 | 不符合學習 C++ 的目標 |

**決定**：方案 B+。
- **C++20**：排程引擎、領域模型、進度分析、離線同步、匯入匯出、語音、AI 製卡、後端 server。
- **TypeScript**：只負責客戶端 UI，透過 WebAssembly 呼叫 C++ 核心。

**理由**
- 最符合「把 C++ 練好」，而且 C++ 部分都是有深度的題材：演算法、並行、網路、記憶體管理。
- UI 是最需要快速迭代、最需要 AI 操作 app 驗證的部分，Web 工具鏈（Playwright、Chrome DevTools）在這方面最成熟。
- 「純邏輯核心不依賴 UI 與平台」這個邊界可以用 CMake target 加 lint 由機器強制，正是倒金字塔第 1 層的示範。

**代價**
- 要維護兩套工具鏈（CMake + Emscripten、Node + TS），P0 的建置成本較高。
- C++ 自訂 lint 規則要寫 clang-tidy 的 AST matcher，比 ESLint 規則難寫。
- 要從基礎學 TypeScript 與前端（Web 經驗不多）。

**備註**：開發平台是 x86 電腦，所以不考慮編譯效能的限制。

## D-005 C++ 標準採用 C++20

- **日期**：2026-11-19
- **狀態**：✅ 已定案

**決定**：C++20。

**理由**
- **concepts**：限制模板參數，讓錯誤用法在編譯期就被擋下（倒金字塔第 1 層）。
- **ranges**：適合進度分析的資料處理管線。
- **coroutines**：適合後端 server 與同步的非同步流程。
- 主流編譯器（GCC、Clang、MSVC）對 C++20 的支援已相當完整；C++20 modules 的工具鏈支援程度則【待查】，P0 時評估是否使用。

**為什麼不選 C++23**：編譯器支援尚不完整，加上 Emscripten（WASM）也要支援，風險較高。之後可以另立一條決策升級。

## D-006 品質策略：倒金字塔，單人縮小版

- **日期**：2026-11-19
- **狀態**：✅ 已定案

**背景**
AI 會大量產生程式碼，需要一套機制讓品質不隨產出量下滑。參考 Lauren Tan〈All Code Is Slop (Except Mine)〉的方法（來源目前只有第三方摘要：[TeamDay](https://www.teamday.ai/ai/lauren-tan-spacexsi-grok-bot-11000-agent-prs-lint-rules)、[AI Engineer Guide](https://aiengineerguide.com/til/all-code-is-slop-except-mine-by-lauren-tan/)）。

**方法摘要**
工程時間依序投入在四層（由多到少）：
1. **程式碼本身**：架構、API 設計、強型別、清楚的邊界，讓錯誤的寫法寫不出來。
2. **靜態分析**：lint 規則、型別系統、測試、CI。
3. **驗證**：讓 AI 實際操作 app、property-based 測試、正規方法。
4. **文字規範**：AGENTS.md、skills、註解，投入最少，因為無法強制執行。

核心原則：**每次糾正 AI，就把那次糾正變成一個確定性的檢查**，而不是在 AGENTS.md 多加一行。

**決定**：採用這個方法，但縮小成單人版。
| 項目 | 處理方式 |
|---|---|
| 第 1、2 層 | **保留**，從 P0 開始建立 |
| lint 規則紀錄簿 | **保留**，每次糾正 AI 都要記錄 |
| AI 操作 app 驗證（第 3 層） | **保留**，P1 起用 Playwright |
| TLA+ 等正規方法（第 3 層） | **延後**到 P3（同步子系統） |
| Lean 證明 | **不納入**計畫，視興趣再決定 |

**理由**
- 原方法是一個團隊花了六個月建立的。單人每週 8 小時，必須排定先後順序。
- 第 1、2 層的成本最低、效果最直接，而且越早建立越好。

**代價**
- 前期功能開發速度慢。
- 數據（例如「每月 11,000 個 PR、revert 率約 0.5%」）來自第三方摘要，未經查證，不能當作預期目標。

**詳細內容**：[`quality-strategy.md`](./quality-strategy.md)

## D-007 不複製 Anki 原始碼

- **日期**：2026-11-19
- **狀態**：✅ 已定案

**背景**
Anki 是最知名的開源間隔重複軟體，很容易想參考它的程式碼。

**決定**
- **不複製、不改寫 Anki 的原始碼**。Anki 採用 AGPL 授權，若複製其程式碼，整個專案就會受到 AGPL 約束。
- **可以**參考 `.apkg` **檔案格式**來實作相容的匯入功能，但程式碼必須自己寫。
- FSRS 參考實作（open-spaced-repetition）採用 MIT 授權，**可以**參考，但要在程式碼與文件中註明出處。各實作的授權以其 repo 實際標示為準，使用前要再確認。

**對 AI 的要求**：在 CLAUDE.md 中明確禁止 AI 貼上 Anki 程式碼，並在 code review 時檢查。

## D-008 可重用工作流做成 skill，以外掛形式載入

- **日期**：2026-11-19
- **狀態**：✅ 已定案

**背景**
開發過程中會反覆出現多步驟的工作流（例如「把一次糾正轉成 lint 規則」「階段回顧」）。如果每次都重新跟 AI 解釋，既浪費時間，結果也不一致。

**選項**
| 選項 | 優點 | 缺點 |
|---|---|---|
| 放在專案 repo 的 `.claude/skills/` | 只對該專案生效，設定最簡單 | 綁死在專案 repo，筆記與工作流分散兩處 |
| 放在 `~/.claude/skills/` | 所有專案都能用 | 不在版本控制內，也不在筆記旁邊 |
| **放在 `ai-driven-se/skill/`，打包成外掛** | 與筆記放在一起、受版本控制、有版本號、可隨時啟用或停用 | 要維護外掛描述檔，更新後需重新安裝 |

**決定**：`ai-driven-se/skill/` 作為 Claude Code 外掛（名稱 `ai-driven-se`），同一個資料夾也提供本機 marketplace（`ai-driven-se-local`），用於長期安裝。使用方式見 [`skill/README.md`](./skill/README.md)。

**理由**
- 工作流是「從專案中學到的東西」，屬於筆記的一部分，應該跟筆記放在一起。
- 外掛有版本號，對應 [08 建構管理](./notes/08-configuration-management.md) 的版本控制原則。

**收錄門檻**：重複出現至少 3 次、多步驟、有驗收方式，而且**無法改成確定性檢查**。能寫成 lint 規則、hook 或 CI 檢查的，就優先那樣做，因為 skill 屬於倒金字塔第 4 層（文字規範），投入順序最後（見 [D-006](#d-006-品質策略倒金字塔單人縮小版)）。

**代價**
- 修改 skill 後要更新 marketplace 並重新啟動 Claude Code 才會生效。試用期間可以改用 `--plugin-dir` 載入。
